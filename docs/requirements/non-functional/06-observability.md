# Observability

方針: 標準的な機能だけで構成し、無料枠に収める。エラーの内容を外部のサービスに送らない。

## Logs

| # | 要件 |
|---|---|
| NFR-20 | 操作ごとに、リクエストを識別する番号、誰の操作か、何の操作か、結果、処理時間、対象の動画を記録する |
| NFR-21 | ログインの資格情報、動画の取得に使う許可情報、メールアドレス、ファイル名は記録しない |
| NFR-22 | 記録の保持期間は 30 日にする |
| NFR-23 | 削除などの操作は、実行した家族と対象を記録する。開発者によるクラウド上の操作の履歴は、90 日間確認できる |

## Metrics

| # | 要件 |
|---|---|
| NFR-24 | 各部品が標準で出す稼働状況の指標を確認できる |
| NFR-25 | 追加で作る指標は、無料枠に収まる 10 個以内にする |
| NFR-26 | 稼働状況は、1 つの画面で確認できる |

## Error Monitoring

| # | 要件 |
|---|---|
| NFR-27 | 想定外の失敗が起きても、発生箇所とリクエストを識別する番号を付けて、エラーとして記録する |
| NFR-28 | サービス側の失敗は必ずエラーとして記録する。利用者側の誤りはエラーにしない (認証の失敗とサイズの不一致は警告として記録する) |
| NFR-29 | 似たエラーをまとめて確認できる |
| NFR-30 | 利用者の端末で起きたエラーも記録する。サービス側のエラーと区別できるようにする |

## Alarms and Notifications

| # | 要件 |
|---|---|
| NFR-31 | 次の条件で通知する (無料枠の 10 個以内) |
| NFR-32 | 通知は、開発者が普段使う連絡手段に届ける。予備としてメールにも届ける。通知は開発者だけが見られる場所に届ける |
| NFR-33 | 通知を受け取る手段から、運用中の環境を変更できないようにする (読み取りだけにする) |
| NFR-34 | 通知から、調査の手がかりにすぐたどれる |

| 条件 | 目安 |
|---|---|
| アプリのエラー記録 | 5 分間に 1 件以上 |
| サーバー側の処理エラー (時間切れ・メモリ不足を含む) | 5 分間に 1 件以上 |
| サービスのサーバーエラー応答 | 5 分間に 1 件以上 |
| 処理の流量制限に達した | 1 件以上 |
| 処理時間 | 制限時間の 8 割に近づいた |
| 月額の費用 | 予算の 80% |
| 認証の失敗・利用者側エラーの急増 | 5 分間に通常の数倍 (値は運用しながら調整) |
